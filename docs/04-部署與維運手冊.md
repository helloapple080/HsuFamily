# 部署與維運手冊

## 必要秘密與設定

| 設定 | 必填 | 原則 |
|---|---|---|
| `MONGO_ROOT_PASSWORD` | 是 | 只供資料庫初始化／管理，不給應用程式 |
| `MONGO_APP_PASSWORD` | 是 | 應用程式最小權限帳號 |
| `JWT_SECRET_KEY` | 是 | 至少 32 字元，建議隨機 256-bit 以上 |
| `ADMIN_PASSWORD` | 首次啟動是 | 高強度、完成首次登入後輪替 |
| `NEXT_PUBLIC_API_URL` | 是 | 在 frontend image build 時設定 |
| `COOKIE_SECURE` | 正式環境是 | 必須為 `true` |
| `ALLOWED_HOSTS` | 正式環境是 | 僅列正式 host，不可 `*` |
| `AllowedOrigins` | 正式環境是 | 僅列正式前端 origin |
| `ProxySettings__KnownProxies__0` | 有 proxy 時 | 填 reverse proxy 固定 IP |

禁止把 `.env`、JWT、MongoDB 密碼或管理員密碼提交到 Git。

## 上線流程

1. 建立正式 DNS 與 TLS 憑證。
2. 將 secrets 放入部署平台 Secret Manager。
3. 以正式 API URL build frontend image。
4. 啟動 MongoDB；等待 health check。
5. 執行 `mongodb-user-init`，確認應用帳號與角色。
6. 啟動 Backend；`/health/live` 與 `/health/ready` 應為 Healthy。
7. 啟動 Frontend，執行登入、CRUD、SignalR smoke test。
8. 確認集中日誌沒有 Token、密碼、姓名或事件標題。
9. 記錄部署版本、image digest、資料庫 migration 與核准人。

## 日常監控

- Availability：live／ready、HTTP 5xx、前端載入失敗。
- Security：登入失敗率、429、refresh replay、異常 IP。
- Performance：API p95／p99、Mongo query latency、SignalR connections。
- Capacity：CPU、memory、disk、Mongo volume、Data Protection key volume。

### Nonce CSP 效能取捨

Frontend 為每個頁面 request 產生一次性 CSP nonce，root layout 因此使用動態 rendering，不再享有靜態頁面最佳化。正式環境應監控 Frontend response latency、CPU 與容量；容量規劃須以 server-rendered request 負載為基準，不可沿用純靜態輸出的估算。

## 備份與還原

- 備份必須加密、限制存取並與主機分離。
- 至少每季執行還原演練，留下耗時與資料完整性證據。
- 正式上線前由業務決定 RPO／RTO；沒有演練的備份不能視為可用。

## 事故處理

1. 確認影響範圍並保留日誌與時間線。
2. 疑似 JWT 外洩：輪替 secret，使既有 access token 全部失效。
3. 疑似 Refresh Token 外洩：撤銷使用者 token family／全部 sessions。
4. 疑似 DB 密碼外洩：先輪替 app password，再檢查權限與存取紀錄。
5. 修復後執行回歸測試、補事故報告與永久控制。

## 發布與回復

- 發布前：CI 必須全綠、變更需 review、image tag 不得使用 latest。
- 回復時只回復應用 image；資料 schema／索引變更要先確認相容性。
- 禁止使用會破壞 volume 的廣域刪除命令。
